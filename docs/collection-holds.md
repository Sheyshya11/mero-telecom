# Collection Hold / Save Hold implementation report

1. **Cause.** The existing form exposed Save Hold to administrators without checking for a collection case. Its API stored a reason without rechecking the balance. The reason blocked suspension, but did not consistently block automated reminders or final warnings.
2. **Central rule.** `collection-hold.policy.ts` derives NONE, ACTIVE, ON_HOLD or RESOLVED from existing invoice collection stages; no duplicate persistent collection status was added. Placement requires an OVERDUE invoice past its due date, an unresolved stage, collectible balance greater than zero, an actionable service context, and no active hold. An active hold can be updated; repeating the same save is idempotent.
3. **Allowed combinations.** ACTIVE / PAST_DUE with overdue debt (including final warning), SUSPENDED with debt, CANCELLED with final debt, and TERMINATED with retained debt allow a hold. The model retains those invoices after termination. No debt, fully paid/credited debt, resolved collection or no overdue case do not allow placement. PENDING never allows placement; pending overdue debt displays a billing-review explanation and a rejected save records a deduplicated data-review audit. Existing cancellation and relocation automation gates remain in force.
4. **Backend validation.** The existing PUT hold endpoint locks the subscription in a serializable transaction, reloads invoices and confirmed payments, applies applicable approved manual credits through the existing account ledger, then invokes the same eligibility policy used by read responses. This rejects a stale form after payment. Reason must contain 3-1000 trimmed characters, notes at most 2000, and an optional deadline must be in the future. Identical concurrent saves create one hold audit. The new POST release endpoint requires `confirmed: true`; a blank reason is no longer a release command.
5. **UI.** Save Hold is hidden when ineligible, with a plain-language explanation. Eligible administrators retain the reason form, with notes and an optional hold-until time. Existing holds show their reason and deadline, and can be updated or released through a confirmation dialog. Staff can read holds and dated history. The customer banner says collection is on hold, keeps the balance visible, and suppresses an imminent suspension warning. Customer subscription responses omit internal reason, notes and actor fields.
6. **Automation pause.** The shared active-hold predicate gates automated warning preparation, durable outbox delivery, queued email delivery, suspension requests and provisioning eligibility. First/second reminders, normal final warning and recovery final warning cannot advance during an active hold. Invoice status, invoice balance, service state and grace/recovery deadlines are not changed by placing a hold. Existing authorized manual reminders and explicit grace extensions remain separate actions. Suspended services remain suspended when a hold is saved.
7. **Resume.** An optional deadline expires when `holdUntil <= now`; reason-only legacy holds remain indefinite until released. The scheduler clears expired or no-longer-actionable holds, reloads current billing state, and runs the existing highest-due-stage logic. Release itself records the action and invalidates cached reads; it does not dispatch reminders or provisioning. The next scheduler pass selects the safe next action instead of sending every missed notice.
8. **Final-warning safety.** If the deadline has passed and a final warning was suppressed by the hold, the existing recovery final warning and immutable 48-hour safety deadline are used. No second recovery mechanism or sliding extension was introduced. No issued final warning means no automatic suspension. A final warning issued before the hold still counts; if it already satisfies the existing deadline checks, an unpaid released account may be suspended on the next scheduler pass. The system continues to distinguish warning acceptance (in-app persistence and email queue acceptance) from actual SMTP delivery.
9. **Payments and credits.** The existing `payableCents` calculation subtracts confirmed payments from the adjusted invoice total; pending/processing payments retain existing protection. A read-only ledger preview allocates available approved manual credits once per customer, respecting service scope and existing applications. Stripe-backed balances continue to use existing invoice/webhook accounting, with no live Stripe changes. Approved manual credits are applied through the existing ledger during overdue reconciliation or a hold save. Confirmed payment clears a resolved hold immediately; credits and other existing invoice balance corrections clear it on reconciliation, without waiting for expiry. Settlement also resolves a held case that had never issued a reminder, including after manual release. Existing NON_PAYMENT restoration is preserved; cancellation/termination and other suspension reasons are not automatically reactivated.
10. **RBAC.** Admin and Super Admin create, update and confirm release. Staff remains read-only for holds and retains its existing manual-reminder access. Customer cannot create, release or read staff collection history. Controller guards and service role checks enforce hold writes.
11. **Audit and migration.** CREATED, UPDATED, RELEASED and EXPIRED hold audits record actor (null for automation), reason, notes, deadlines and timestamp. Expiry/release retain the old reason and creation metadata in audit history. The additive `20261007120000_collection_hold_management` migration reuses `collectionHoldReason` and adds notes, deadline, created actor/time and released actor/time. Existing reason-only holds are preserved with their last-known update time; no creator is fabricated. No invoice/service enums were changed.
12. **Verification.** API unit tests: **567 passed across 78 suites**. Frontend tests: **177 passed across 38 files**. Collection/notification integration tests: **44 passed across 2 suites**. Typecheck and lint passed. Changed-file formatting passed. Regression coverage includes eligible service states; paid, zero, resolved and pending rejection; partial payments and credits; credit allocation scope and single-use budgets; duplicate concurrent saves; suppressed automated and queued warnings; expiry past the original deadline; fixed recovery timing; confirmed release; stale forms; payment/restoration; credit settlement before the first reminder; role enforcement; customer privacy; customer hold messaging; and staff history.
